**3.1** **Low Risk**


**3.1.1** **Initial super deployments accept invalid anchors**


**Severity:** Low Risk.


**Context:** [OPContractsManagerV2.sol#L720-L790.](https://cantina.xyz/code/a7b3d922-fd5a-4e5d-ab4d-559a5ea1e2cb/packages/contracts-bedrock/src/L1/opcm/OPContractsManagerV2.sol#L720-L790)


**Description:** <mark>_assertValidFullConfig</mark> accepts any nonzero initial anchor below <mark>uint64.max</mark> .

When a permissionless game is enabled, it only excludes the exact <mark>0xdead</mark> placeholder. U20 commit

[9714d4dd2c77052fad62505598db3568b1458f7d (PR 21720) also newly permits](https://github.com/ethereum-optimism/optimism/commit/9714d4dd2c77052fad62505598db3568b1458f7d) <mark>SUPER_CANNON_KONA</mark>
to be the respected game at initial deployment. The function never proves that the supplied root
is the chain's SuperV1 genesis commitment or that its sequence is a timestamp the challenger can
retrieve.


For example, a chain operator can accidentally supply a legacy V0 output root and L2 block number. <mark>OPContractsManagerV2.deploy</mark>, the canonical <mark>DeployOPChain</mark> script, and <mark>OPContractsManager</mark>


<mark>StandardValidator</mark> all accept that tuple. A fresh <mark>AnchorStateRegistry</mark> then exposes it as the
starting proposal for permissionless super games.


An arbitrary proposer can create a correctly encoded super game one sequence later. The production challenger rejects the starting block number as a pre-genesis timestamp, so it cannot create a
player. The unopposed claim expires into <mark>DEFENDER_WINS</mark> and becomes claim-valid. Consequently, its
attacker-selected per-chain output root can authorize fabricated withdrawals from all ETH or tokens
later held by the portal and lockbox.


The official <mark>op-deployer</mark> prepare pipeline computes the correct genesis proposal, which reduces
likelihood. The public OPCM API and supported Forge deployment script still accept the malformed
tuple. The repository's own permissionless deployment fixture uses an arbitrary non-placeholder root
and sequence.


**Recommendation:** Do not allow a fresh chain to respect a permissionless super game based only on a
caller-supplied <mark>Proposal</mark> . Bootstrap with <mark>SUPER_PERMISSIONED</mark>, then permit <mark>SUPER_CANNON_KONA</mark>
only after a trusted, canonical super game has installed an authenticated genesis or later anchor.
If direct permissionless bootstrap remains supported, require a proposal attested by the prepared
genesis process and make both <mark>DeployOPChain</mark> and <mark>OPContractsManagerStandardValidator</mark> reject
values that do not match it.


**OP Labs:** Acknowledged. The starting anchor is a trusted deployment input whose correctness is
checked offchain by the operator and the supported <mark>op-deployer</mark> flow calculates it.


**Cantina Managed:** Acknowledged.


**3.1.2** **<mark>StandardValidator</mark>** **accepts arbitrary same-version super-permissioned game implementa-**
**tions**


**Severity:** Low Risk.


**Context:** [StandardValidatorUtils.sol#L492-L496.](https://cantina.xyz/code/a7b3d922-fd5a-4e5d-ab4d-559a5ea1e2cb/packages/contracts-bedrock/src/L1/opcm/StandardValidatorUtils.sol#L492-L496)


**Description:** The U20 <mark>StandardValidator</mark> stores the release's approved <mark>superPermissioned</mark>


<mark>DisputeGameImpl</mark> address and passes it into the new specialized SPDG validation path. However,


<mark>assertValidSuperPermissionedDisputeGame</mark> does not compare the factory's registered implemen
tation with that address. It calls <mark>version()</mark> on both contracts and accepts equality between the
returned strings.


The registered candidate controls its own <mark>version()</mark> result. A different implementation can there
fore report <mark>1.0.0</mark>, retain the canonical packed ASR and proposer arguments and make the validator
return an empty success string. The other SPDG checks authenticate only the ASR and the proposer
bytes stored by the factory; they do not prove that the registered implementation enforces those
arguments or any game semantics.

This defeats the validator's stated purpose of ensuring that L1 contracts are configured correctly
before and after an upgrade. The production SPDG enforces proposer authorization, well-formed
calldata, root-claim binding to a decoded super-root preimage and a sequence newer than the anchor.
A same-version substitute can omit all of these checks. Once cloned by the factory, it can allow
an untrusted caller to create an immediately defender-winning game whose <mark>rootClaimByChainId</mark>
returns an attacker-selected output root committing to fabricated MessagePasser state. After the
normal ASR air gap, that game is claim-valid and can authorize fabricated withdrawal proofs through

<mark>OptimismPortal2</mark> .


During an upgrade or manual recovery, the DGF owner can register an incorrect, compromised or
lookalike implementation while retaining the canonical packed ASR and proposer arguments. The
substitute reports the official <mark>1.0.0</mark> version, so <mark>OPContractsManagerStandardValidator.validate</mark>


<mark>(...,</mark> <mark>false)</mark> returns an empty success string even though the implementation is different. An

arbitrary account can then create a <mark>DEFENDER_WINS</mark> game with an attacker-selected output root.
The factory registration, respected-game flag, resolution timestamp and normal ASR air gap make
the game claim-valid, allowing the attacker to prove and finalize a withdrawal against the fabricated
root and release portal or shared-lockbox assets. The condition requires a privileged implementation
change, giving it low-to-moderate likelihood; exploitation after that change is permissionless and
requires only the ordinary finality and proof delays.


**Recommendation:** Require <mark>game.gameAddress</mark> <mark>==</mark> <mark>_impls.expectedGameImpl</mark> in <mark>assertValidSuper</mark>


<mark>PermissionedDisputeGame</mark> ; do not use a value returned by the candidate itself as identity evidence.
If operational requirements permit multiple approved builds, validate an immutable allowlist of exact
runtime code hashes or implementation addresses. Apply the same identity rule to every standard
and migration validator path and add a negative test where a different implementation returns the
expected version and canonical getters.


**OP Labs:** [Fixed in commit 283bb45.](https://github.com/ethereum-optimism/optimism/commit/283bb456cf5b17f407f8f72826820d3852d966fe)


**Cantina Managed:** Fix verified. <mark>StandardValidator</mark> now requires the factory's registered <mark>SUPER_</mark>


<mark>PERMISSIONED</mark> implementation to equal the release-approved implementation address. A same-version

lookalike is rejected with <mark>SPDG-150</mark> .

**3.1.4** **Super-root migration can retain a legacy anchor and leave permissionless invalid claims unchal-**
**lengeable**


**Severity:** Low Risk.


**Context:** [OPContractsManagerV2.sol#L324-L344,](https://cantina.xyz/code/a7b3d922-fd5a-4e5d-ab4d-559a5ea1e2cb/packages/contracts-bedrock/src/L1/opcm/OPContractsManagerV2.sol#L324-L344) [OPContractsManagerV2.sol#L362-L367,](https://cantina.xyz/code/a7b3d922-fd5a-4e5d-ab4d-559a5ea1e2cb/packages/contracts-bedrock/src/L1/opcm/OPContractsManagerV2.sol#L362-L367) [OPCon-](https://cantina.xyz/code/a7b3d922-fd5a-4e5d-ab4d-559a5ea1e2cb/packages/contracts-bedrock/src/L1/opcm/OPContractsManagerV2.sol#L671-L678)

**Description:** U20 changes <mark>SUPER_ROOT_GAMES_MIGRATION</mark> from opt-in to unconditionally enabled

and extends the release allowance for <mark>overrides.cfg.startingAnchorRoot</mark>, but never requires the
instruction when an upgrade disables the legacy output-root games and enables a super-root game.

<mark>_loadFullConfig</mark> falls back to <mark>AnchorStateRegistry.getStartingAnchorRoot()</mark> when that instruc
tion is absent. This is not the current anchor when <mark>anchorGame</mark> is set: the current anchor is the

legacy game's output root and L2 block number. <mark>_assertValidFullConfig</mark> validates the anchor only

for initial deployments, so the upgrade and the post-upgrade <mark>StandardValidator</mark> both accept this
mixed state.


The subsequent <mark>AnchorStateRegistry.initialize</mark> call receives the unchanged original starting root.

Its <mark>rootChanged</mark> check is therefore false and it does not clear the existing legacy <mark>anchorGame</mark> . New


<mark>SuperFaultDisputeGame</mark> instances consequently copy the legacy output-root hash and L2 block

number into <mark>startingProposal</mark>, although the super trace interprets that number as a timestamp
and the hash as a super-root commitment.


This breaks the honest challenger before any onchain move is made. The challenger constructs its top
prestate with <mark>SuperRootAtTimestamp(legacyL2BlockNumber)</mark> . For a normal OP chain, the legacy block

number is far below the L2 genesis Unix timestamp, so <mark>op-node</mark> rejects it in <mark>TargetBlockNumber</mark>

as pre-genesis. That provider error is not <mark>ErrInvalidPrestate</mark> ; the scheduler therefore refuses to

create the game player even when <mark>allow-invalid-prestate</mark> is enabled.


Because of this issue, after an accepted but incomplete U20 migration, any account can create a permissionless <mark>SUPER_CANNON_KONA</mark> game with an arbitrary, correctly encoded super root at sequence

number <mark>N</mark> <mark>+</mark> <mark>1</mark> . Because honest challengers cannot instantiate a trace for the retained legacy

prestate, no counter is posted. Once the game clock expires it resolves <mark>DEFENDER_WINS</mark> ; after the

finality delay, the <mark>AnchorStateRegistry</mark> treats it as a valid anchor. The attacker's per-chain output

root can then be used to prove fabricated withdrawals through <mark>OptimismPortal2</mark>, putting all ETH
and tokens secured by that portal at risk.


The precondition for this issue to be triggered is an otherwise authorized U20 migration that installs the super game family but omits one optional-looking extra instruction, followed by normal
guardian activation of the permissionless super game (or a migration that selects it immediately).
For example, suppose a permissionless chain has a finalized legacy output-root game as its anchor
at L2 block N . If the chain's <mark>ProxyAdmin</mark> owner disables legacy games, enables the super game

family and omits <mark>overrides.cfg.startingAnchorRoot</mark>, <mark>OPContractsManagerV2.upgrade</mark> succeeds,

retains the legacy <mark>anchorGame</mark> and the <mark>StandardValidator</mark> returns no errors. Once the guardian

selects <mark>SUPER_CANNON_KONA</mark> as respected, an unprivileged attacker can create a super game con
taining an attacker-selected output root at timestamp <mark>N</mark> <mark>+</mark> <mark>1</mark> and pay the configured initial bond.

Honest challengers query <mark>superroot_atTimestamp(N)</mark>, but <mark>op-node</mark> rejects N as pre-genesis, so
the scheduler never creates a player. The attacker waits for the game clock and finality delay, resolves
the uncontested root as <mark>DEFENDER_WINS</mark>, closes the game and uses the now-valid anchor to prove
and finalize withdrawals against the attacker-selected per-chain output root. This is a realistic configuration failure rather than a compromised-admin attack: the code comment says the migration requires
the override, the public upgrade API does not enforce that requirement and the <mark>StandardValidator</mark>

guardian has the dispute/finality window to detect and blacklist a malicious game.

that the supplied root is nonzero, that its sequence number is a valid timestamp strictly greater than
the current <mark>getAnchorRoot()</mark> sequence and ensure the legacy <mark>anchorGame</mark> is cleared atomically.

The <mark>StandardValidator</mark> should also reject a super-root configuration whose active anchor is still a
legacy game type. If feasible, have migration tooling supply the encoded super-root preimage and
verify its hash, rather than accepting an unbound hash alone.

upgrade task or a manual verification process.

**3.1.5** **<mark>SuperPermissioned</mark>** **game initialization can trap a configured bond**


**Severity:** Low Risk.


**Context:** [SuperPermissionedDisputeGame.sol#L45-L62, OPContractsManagerV2.sol#L749-L764.](https://cantina.xyz/code/a7b3d922-fd5a-4e5d-ab4d-559a5ea1e2cb/packages/contracts-bedrock/src/dispute/SuperPermissionedDisputeGame.sol#L45-L62)


**Description:** The standalone <mark>SuperPermissionedDisputeGame.initialize</mark> function is payable, but
the game has no bond accounting, distribution, or withdrawal path for an initialization value. A nonzero
initialization bond sent to a <mark>SuperPermissioned</mark> clone therefore remains trapped in that clone.


The normal U20 configuration validator checks that <mark>SUPER_PERMISSIONED</mark> has a zero initialization
bond, but the game implementation itself does not enforce that invariant. Any configuration path
that supplies a nonzero bond can consequently create publicly usable game clones that hold unrecoverable ETH. Malformed privileged game configuration can permanently lock ETH in each created

<mark>SuperPermissioned</mark> clone. The amount is bounded per clone, but the condition is repeated for every
game created under the affected configuration.


**Recommendation:** Make the <mark>SuperPermissioned</mark> initializer nonpayable if it must never receive a

bond, or explicitly reject nonzero <mark>msg.value</mark> and enforce the zero bond invariant at every configuration mutation path. Add a balance conservation test for clone creation.

**Cantina Managed:** Fix verified. <mark>SuperPermissionedDisputeGame.initialize</mark> now rejects any nonzero


<mark>msg.value</mark> with <mark>IncorrectBondAmount</mark> before completing initialization.
