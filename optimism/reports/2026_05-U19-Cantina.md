**3.1.1** **L2CM drops X Layer liquidity minters**


**Severity:** Medium Risk


**Context:** [L2ContractsManager.sol#L224-L245](https://cantina.xyz/code/b643b060-0b82-470b-8941-45e1dfaa2e33/packages/contracts-bedrock/src/L2/L2ContractsManager.sol#L224-L245)


**Description:** _loadFullConfig has a special fallback for the documented X Layer

LiquidityController fork when owner() reverts, but it snapshots only the owner fallback
plus token name and symbol. It does not snapshot existing authorized minters and does not require
any explicit reauthorization data.


_apply then installs the OP Stack LiquidityController and calls initialize with only those three
fields. The new implementation inherits OwnableUpgradeable before minters, so its minters mapping is at slot 101. A no- owner() fork that authorizes minters from its own first mapping stores those
authorizations at slot 1. Therefore a successful L2CM upgrade preserves the owner and metadata while
silently leaving previously authorized minters unreadable by the new implementation.


With SYS_FEATURE__CUSTOM_GAS_TOKEN=true, the old minter is authorized before

_executeUpgrade(), upgraded.minters(minter) is false after the upgrade and mint reverts
with LiquidityController_Unauthorized until the proxy admin owner manually reauthorizes the
minter. Existing bridge, migration or operational native-asset liquidity minters can therefore halt after the
upgrade even though the upgrade transaction itself succeeds.


**Recommendation:** Make minter preservation explicit for the X Layer compatibility migration. Either fail
preflight unless the upgrade bundle includes the required minter reauthorization list and post-upgrade
validation, or add a fork-specific migration that copies the known minter slots or authorizations before
native-asset minting and burning resume.


**3.1.2** **OPCM utils allows unsupported v5 initializers**


**Severity:** Medium Risk


**Context:** [OPContractsManagerUtils.sol#L343-L359](https://cantina.xyz/code/b643b060-0b82-470b-8941-45e1dfaa2e33/packages/contracts-bedrock/src/L1/opcm/OPContractsManagerUtils.sol#L343-L359)


**Description:** OPContractsManagerUtils.upgrade tries to reject OpenZeppelin v5 Initializable
contracts by checking the caller-supplied slot and the target proxy's ERC-7201 initializer slot before the
final upgrade. That only detects proxies that already have v5 initializer state.


A proxy that currently uses the v4 layout has an empty ERC-7201 slot, so it passes the guard. If the incoming
implementation uses the v5 initializer layout, upgradeAndCall then delegates to its initializer and writes

_initialized into the ERC-7201 slot. The helper has now installed an implementation that its own guard
says is unsupported.


Consequently, the next standard OPCM upgrade for that proxy reverts before it can repair or replace
the implementation, because the same guard now sees the nonzero ERC-7201 slot. A single release that
accidentally includes a v5-style implementation can leave the proxy outside the normal OPCM upgrade
mechanism until a custom recovery helper or manual storage fix is used.


Example:


1. A proxy currently points to a v4-style implementation.


2. The proxy's v5 ERC-7201 initializer slot is empty.


3. A release accidentally provides a v5-style implementation.


4. OPContractsManagerUtils.upgrade checks the v5 slot and sees bytes32(0), so it does not revert.


5. The helper clears the old v4 initializer byte.


6. The helper calls upgradeAndCall with the new implementation.


4


7. The new implementation's initializer writes to the v5 ERC-7201 initializer slot.


8. The upgrade succeeds, even though OPCM says v5 initializer state is unsupported.


9. The next standard OPCM upgrade checks the same v5 slot, now sees a nonzero value, and reverts
with OPContractsManagerUtils_OZv5InitializableUnsupported .


**Recommendation:** Make the unsupported initializer-layout rule apply to the incoming implementation
before it is installed. If OPCM intends to reject v5 initializers, require release implementations to expose a
supported-layout marker or enforce an implementation codehash/metadata allowlist that upgrade can
check before upgradeAndCall .


If v5 implementations should be allowed, support that layout deliberately instead: clear the ERC-7201

_initialized field and check the v5 _initializing flag.


**3.1.3** **Separate FeeVault route setters can misroute accrued fees**


**Severity:** Medium Risk


**Context:** [FeeVault.sol#L113-L163](https://cantina.xyz/code/b643b060-0b82-470b-8941-45e1dfaa2e33/packages/contracts-bedrock/src/L2/FeeVault.sol#L113-L163)


**Description:** FeeVault stores recipient and withdrawalNetwork as separate fields and the proxy
admin owner must update them with separate calls. withdraw is permissionless and always withdraws
the full vault balance to whatever pair is stored at that moment.


This creates an unsafe intermediate state when an operator changes a vault from an L1 recipient to an
L2 recipient or the reverse. If the owner updates withdrawalNetwork first, anyone can call withdraw
before recipient is updated and send the full balance to the old recipient address on the new network.
If the owner updates recipient first, anyone can create a withdrawal to the new recipient address on
the old network.


Both the old and new configurations can be valid. The problem is the transient cross-product created by
independent setters. This matters for contract recipients such as Safes, treasuries or network-specific
payout contracts because the same 20-byte address may not be controlled on the other network. A public
caller can therefore turn a routine route migration into a full-balance transfer or L1 withdrawal message
to an address that the intended recipient cannot recover from.


**Recommendation:** Add an atomic route update function that sets recipient and

withdrawalNetwork together, and deprecate separate route changes for cross-network migrations. For
example:


**function** setWithdrawalRoute( **address** _newRecipient, Types.WithdrawalNetwork

_�→_ _newWithdrawalNetwork) **external** {
_assertOnlyProxyAdminOwner();
**require** (_newRecipient != **address** (0), "FeeVault: zero recipient");


**address** oldRecipient = recipient;
Types.WithdrawalNetwork oldWithdrawalNetwork = withdrawalNetwork;


recipient = _newRecipient;
withdrawalNetwork = _newWithdrawalNetwork;


emit RecipientUpdated(oldRecipient, _newRecipient);
emit WithdrawalNetworkUpdated(oldWithdrawalNetwork, _newWithdrawalNetwork);
}


If the separate setters must remain for compatibility, document that operators must first reduce exposure
by withdrawing the vault balance or raising the minimum above the current balance, then execute the
route change atomically through a batching wallet or migration contract.

**3.2.4** **Renounced SystemConfig owner blocks normal OPCM upgrades**


**Severity:** Low Risk


**Context:** [SystemConfig.sol#L223-L225](https://cantina.xyz/code/b643b060-0b82-470b-8941-45e1dfaa2e33/packages/contracts-bedrock/src/L1/SystemConfig.sol#L223-L225)


**Description:** SystemConfig inherits OwnableUpgradeable and does not override

renounceOwnership . Therefore, the current SystemConfig.owner() can call the inherited function and set the owner to address(0) .


That zero owner breaks normal OPCMv2 upgrades. OPCMv2 loads the current SystemConfig.owner()
into FullConfig.systemConfigOwner and passes that value back into SystemConfig.initialize .
If ownership has been renounced, the initializer receives address(0) . It then calls

transferOwnership(_owner) and OpenZeppelin rejects the zero address.


This means a SystemConfig whose ownership was renounced can block standard OPCMv2 upgrades
even when the chain ProxyAdmin owner is still valid. Recovery requires a non-standard proxy-admin
action or a special migration instead of the intended audited release process.


**Recommendation:** Override renounceOwnership in SystemConfig and make it revert, or use an
ownership primitive that does not expose irreversible renounce behavior for this contract. If zero-owner

SystemConfig instances must be recoverable, add an explicit OPCMv2 recovery instruction that can set
a new nonzero owner with strict validation.

**3.2.7** **Validator misses portal** **AnchorStateRegistry** **check**


**Severity:** Low Risk


**Context:** [StandardValidatorUtils.sol#L256-L280](https://cantina.xyz/code/b643b060-0b82-470b-8941-45e1dfaa2e33/packages/contracts-bedrock/src/L1/opcm/StandardValidatorUtils.sol#L256-L280)


**Description:** The validators do not directly validate the AnchorStateRegistry configured on each
portal.


StandardValidatorUtils.assertValidOptimismPortal() checks portal.disputeGameFactory(), but

OptimismPortal2 derives that value from portal.anchorStateRegistry().disputeGameFactory() . A
wrong registry can return the expected DGF and still fail the normal ASR checks for implementation, proxy
admin, SystemConfig, or registry behavior.


The migration validator has the same missing check. It discovers the shared ASR from the first portal,
checks that every portal reports the same ASR, and checks that this ASR has a super respected game type.
It does not require the portal ASR to match the ASR encoded in the validated shared dispute-game args.


This is a release-gate validation gap. It requires bad or malicious deployment/migration configuration
because unprivileged users cannot install the wrong ASR. If that configuration is accepted, the portal's
withdrawal finality checks use an unchecked registry.


**Recommendation:** Validate each portal's anchorStateRegistry() before certifying the portal or migration.


For standard validation, fetch IAnchorStateRegistry asr = _portal.anchorStateRegistry() and run
the existing ASR checks against it. For migration validation, also require the ASR used by each portal to
match the ASR decoded from the validated shared dispute-game args.

If the expected owner can differ from l1PAOMultisig, add a dedicated validation input or override field instead of silently accepting any owner. For migrated chains, validate each chain's
SystemConfig.l2ChainId() against the migration manifest and ensure super-root proof validation
uses that same value consistently. Consider also validating batchInbox() and startBlock() because

**3.2.10** **Unauthorized root-block challenge wins bond**


**Severity:** Low Risk


**Context:** [PermissionedDisputeGame.sol#L37-L68](https://cantina.xyz/code/b643b060-0b82-470b-8941-45e1dfaa2e33/packages/contracts-bedrock/src/dispute/PermissionedDisputeGame.sol#L37-L68)


**Description:** PermissionedDisputeGame gates step and move with onlyAuthorized, but it does
not override the inherited challengeRootL2Block function. The inherited function is still externally
callable by anyone. When its proof checks pass, it records l2BlockNumberChallenger = msg.sender .


During root subgame resolution, FaultDisputeGame.resolveClaim treats that recorded address as the
winner of the root claim bond. Consequently, any account can submit the root L2 block number challenge
for a permissioned game and become the recipient of the proposer's root bond. The account does not
need to be the configured proposer or challenger.


This does not allow an invalid root claim to finalize. The challenge still requires a valid output-root proof
and a block header whose number differs from the claimed L2 block number. The problem is the mismatch
with the permissioned game model: this game is meant to restrict dispute participation to the configured
proposer and challenger, but this challenge can be taken by anyone. As a result, the configured challenger
does not exclusively control the root-block challenge, and an arbitrary caller can capture the bond reward
when this special challenge is available.


**Recommendation:** Override challengeRootL2Block in PermissionedDisputeGame and apply the
intended permission check. If both permissioned roles are meant to perform this challenge, use
onlyAuthorized . If the bond reward should be reserved for the challenger role, require msg.sender ==

challenger() .

**3.3.1** **ASR cutovers can leave old games valid**


**Severity:** Informational


**Context:** [AnchorStateRegistry.sol#L151-L170](https://cantina.xyz/code/b643b060-0b82-470b-8941-45e1dfaa2e33/packages/contracts-bedrock/src/dispute/AnchorStateRegistry.sol#L151-L170)


10


**Description:** AnchorStateRegistry lets the guardian change the respected game type and the retirement cutoff only through two separate calls. updateRetirementTimestamp() retires games created at or
before the current timestamp, while setRespectedGameType() changes which game type new games
will snapshot as respected.


That split leaves no atomic way to retire old games and switch the respected game type. If the guardian
updates the retirement timestamp first, any public caller can create a game of the old respected type in a
later block before the respected type is changed. That game records wasRespectedGameTypeWhenCreated

== true . It is also newer than retirementTimestamp, so isGameRetired() returns false. After the
guardian switches to the new game type, isGameRespected() still accepts the old game because it only
reads the creation-time snapshot.


Consequently, the old game can later resolve DEFENDER_WINS, pass isGameClaimValid() and call

setAnchorState() . The same predicate is used by OptimismPortal2.checkWithdrawal(), so withdrawal finalization can also keep trusting a game type that the guardian meant to retire during the cutover.


This matters during emergency or proof-system transitions. If the old game type is being retired because
it is unsafe, unavailable or incompatible with the new proof mode, a public caller can preserve one old
game past the cutoff and later use it as an anchor or withdrawal root if it is not successfully challenged.


**Recommendation:** Add an atomic guardian operation that sets the new respected game type and retirement timestamp in the same call. The function should retire games created at or before the transaction
timestamp and switch respectedGameType before any later transaction can create another old-type
game with a respected snapshot.


For upgrade-driven cutovers, use the same atomic operation or add an explicit initializer mode that
advances the retirement timestamp when the respected game type changes.

the game interface can verify at runtime.
