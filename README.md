# Audit dataset

Goal: for each L2BEAT-tracked project and for widely reused code, collect the public audit reports, extract exactly which source files and revisions were audited, and fetch those audited sources. The dataset records audit evidence only.

Comparing it with the code deployed onchain happens on the L2BEAT side, which reads the evidence through the [audit export](#audit-export): `audit-index.json` and `audit-objects.json.zst`.

## Repository structure

- `<project>/` (e.g. `tornado-cash/`, `scroll/`, `unichain/`): one collection per project, named by the project's L2BEAT id, containing:
  - `reports/`: original audit reports (PDF, HTML) and their Markdown conversions; `reports/irrelevant/` holds reports out of scope for onchain/zk code. A collection whose reports were searched for and found absent keeps an empty `reports/` directory.
  - `audit-summary.json`: machine-readable extraction of every report: relevance, audited repositories, paths with their kind (`evm`, `zk`, `cairo` or `other`; only `evm` paths are fetched and exported today), revisions with their GitHub committer timestamps, statuses and the identifiers of open major findings. Repository ids are canonical (`owner/repo` for GitHub), see `python3 -m audit_dataset repository-id`.
  - `audit-summary.md`: human-readable rendering of `audit-summary.json`.
  - `audited-sources/`: the EVM source files of `evm` paths, fetched at the exact audited commits and laid out as `<owner>/<repo>/<commit>/<path in the repository>`, with a `manifest.json` listing, per audited `(repository, path, commit)`, the files stored for it, the versions that were not fetched (unpinned revisions, paths of other kinds), the sources that could not be fetched, and the files left out (fetched `.gitignore`-style files and submodules). Each stored file carries `git_object`, the upstream blob id, and `sha256` of the file as stored, i.e. after formatting. The layout and the manifest schema are documented in `audit_dataset/manifest.py`.
- `_libs/<vendor>/`: collections for widely reused code (OpenZeppelin, Safe, Solady, Solmate, SP1, eth-infinitism). Same layout and commands as a project collection; the grouping is organizational only.
- `repositories.json`: registry of every repository referenced by any collection: URL and, for forks, the canonical id of the upstream repository under `fork_of`. Generated by the `repositories` command; entries with `"manual": true` are kept across regenerations.
- `collections.json`: the display name of every collection, by collection id (`<project>` or `_libs/<vendor>`), sorted, maintained by hand: the project's name on L2BEAT, or the vendor's name. The export requires it to name exactly the collections.
- `audit-index.json` and `audit-objects.json.zst`: the audit export, the only public interface of the dataset. Generated by the `export` command, see [Audit export](#audit-export).
- `foundry.toml`: the forge fmt configuration used for every Solidity file in the dataset, exported by the `format` command so consumers can format deployed sources identically.
- `audit_dataset/`: the Python package behind `python3 -m audit_dataset`, see [Pipeline](#pipeline).
- `skills/audit-extract/`: instructions for the agent that classifies reports and produces `audit-summary.json`. `skills/double-check-extraction/`: instructions for an independent re-extraction that is compared with the committed one.

## Pipeline

Requirements: Python 3.14 (the export uses `compression.zstd`), git, Foundry's `forge` for formatting, the authenticated GitHub CLI `gh` for fork lineage, and `pymupdf4llm` for PDF conversion only: `python3 -m venv .venv && .venv/bin/pip3 install pymupdf4llm==1.28.2`.

Every command takes collection names (`scroll`, `safe` or `_libs/safe`) or `--all`; `python3 -m audit_dataset --help` lists them.

1. `.venv/bin/python3 -m audit_dataset pdf-to-md <collection>`: converts every PDF under `<collection>/reports` to Markdown, skipping PDFs that already have one.
2. Run an agent on `skills/audit-extract/SKILL.md` for the collection to classify all Markdown reports found recursively under `<collection>/reports` and extract `<collection>/audit-summary.json`. Irrelevant reports are moved to `<collection>/reports/irrelevant`, retained in the summary with a short description, and excluded from source extraction.
3. `python3 -m audit_dataset pipeline <collection>` runs the remaining steps in order. They can also be run individually:
   - `render <collection>`: validates the summary (schema, canonical repository ids, statuses, major finding ids, report files, timestamps) and writes `<collection>/audit-summary.md`. Human review of the Markdown is recommended.
   - `fetch <collection>`: fetches every `evm` path of a relevant report that is pinned to a full Git commit and not marked `not_audited` into `<collection>/audited-sources`, reading blobs from a bare clone. Branches, tags and pull requests without a resolved commit, commit ranges, abbreviated commits and paths of other kinds are recorded as skipped in `manifest.json`; `--kinds evm,zk` fetches zk paths as well. A directory scope stores only the source files of its kind (`.sol`, `.yul`, `.vy` for `evm`), a file scope stores its file whatever the extension. Relative symlinks that stay within the repository are resolved from the same commit and stored as regular files.
   - `format <collection>`: reformats every Solidity file under `audited-sources` with the shared forge fmt config and exports that config to `foundry.toml`. `--check` reports unformatted files without changing them.
   - `index <collection>`: verifies that every stored file is listed in `manifest.json` with its exact spelling, that no two stored names differ only by letter case, and records the post-format `sha256` of every file.
   - `repositories`: rebuilds `repositories.json` from every collection, asking GitHub for fork lineage (`--no-lookup` keeps previously known lineage).
   - `export`: regenerates `audit-index.json` and `audit-objects.json.zst` from every collection. Requires a `collections.json` entry for every collection, so add one for a new collection. Commit both files with the collection change.

## Audit export

`audit-index.json` and `audit-objects.json.zst` at the repository root are the dataset's public interface. Everything else (summaries, manifests, `audited-sources/`, the package) is internal and may change as long as the export keeps its shape. L2BEAT reads both files pinned to a dataset commit:

```
https://raw.githubusercontent.com/<owner>/audit-dataset/<commit>/audit-index.json
https://raw.githubusercontent.com/<owner>/audit-dataset/<commit>/audit-objects.json.zst
```

and uses them to find, for every contract, library, interface and free function a project deployed, the closest audited code and the reports that audited it. It links a report's original document, and fetches a single object without the bundle, as:

```
https://github.com/<owner>/audit-dataset/blob/<commit>/<document>          see document
https://api.github.com/repos/<owner>/audit-dataset/git/blobs/<blobId>      see audit-objects.json.zst
```

The export only says where audited code lives, who audited it, which major findings were open there, and what the audited code was; L2BEAT parses and compares the Solidity itself, so formatting does not matter to it.

### `audit-index.json`

```ts
type AuditIndex = {
  schema_version: '1.1.0'
  collections: Record<CollectionId, Collection>
  reports: Record<ReportId, Report>
  repositories: Record<RepositoryId, Record<Commit, Snapshot>>
}

type Collection = {
  name: string                // display name, e.g. "OpenZeppelin", "Safe", "Privacy Pools"
  kind: 'project' | 'library' // 'library' exactly for the ids under "_libs/"
}

type Report = {
  collections: CollectionId[] // the collections the report belongs to, sorted, e.g. ["ethscriptions", "facet"] or ["_libs/safe"]
  title: string
  auditor: string
  date: string | null         // YYYY-MM-DD
  document: string            // dataset path of the report's original document,
                              // e.g. "tornado-cash/reports/ABDK - Tornado Cash Anonymity Mining Final Audit.pdf"
}

// One repository at one commit, as pinned by the audits.
type Snapshot = {
  timestamp: number                                     // committer date, unix seconds
  files: Record<Path, ObjectId>                         // every audited file at this commit -> its contents in the bundle
  audits: Record<ReportId, Record<Path, FindingId[]>>   // report -> scoped path (a file or a directory) -> major findings open there
}

type CollectionId = string // collection directory: an L2BEAT project id such as "tornado-cash", or "_libs/<vendor>" such as "_libs/safe"
type ReportId = string     // the summary's report id, unique across the dataset
type RepositoryId = string // canonical id: "owner/repo", "gist/owner/id" or "<host>/<path>"; it determines the URL
type Commit = string       // full lowercase hex commit id (40, or 64 for SHA-256 repositories)
type ObjectId = string     // first 12 lowercase hex characters of the git blob id of the contents
type Path = string         // POSIX, relative to the repository root, no leading or trailing "/"
type FindingId = string    // as in the version's major_finding_ids
```

A collection is a dataset directory of audits. A `project` collection holds the audits of one L2BEAT project and its id is that project's L2BEAT id; a `library` collection, under `_libs/`, holds the audits of code that many projects reuse. Names come from `collections.json`.

`reports` lists every relevant report of every collection. The snapshots' `audits` name only the reports that audited exported Solidity files, so a report that reviewed circuits, Cairo or Rust code, cryptography, or code pinned only to a branch is listed without appearing in any snapshot.

`document` is the POSIX path, relative to the dataset root, of the file the report was published as: the first of `.pdf`, `.html`, `.csv` and `.js` that exists next to the report's Markdown conversion (a PDF wins over an HTML copy), or the Markdown itself for a report published as Markdown. A report in several collections links the copy in the first of them by id; the copies are identical (rule 5). The path names a committed file with exactly that letter case, so it can be linked, with each path segment percent-encoded, as `https://github.com/<owner>/audit-dataset/blob/<commit>/<document>`: GitHub renders PDFs there, while raw URLs download them.

A file is audited by a report when one of the report's scoped paths is the file itself or a directory above it: `src` covers `src/Vault.sol`, `src/Vault` does not. A directory audit is written once under its directory path, never copied onto every file below it.

`audits[report][path]` is the summary version's `major_finding_ids`: the Major/Critical findings that report left open in that path at that commit, in report order, or `[]` when it has none. Identifiers are copied verbatim, without titles, severities or statuses.

Repository URLs are not exported, because the canonical id determines them, for every entry of `repositories.json`:

- an id whose first segment contains a dot is `<host>/<path>` on another host, at `https://<host>/<path>` (GitHub owners never contain a dot);
- `gist/<owner>/<id>` is the gist at `https://gist.github.com/<owner>/<id>`;
- every other id is `<owner>/<repo>`, at `https://github.com/<owner>/<repo>`.

### `audit-objects.json.zst`

One zstd frame (level 19, `--long=27`: long-distance matching with a 128 MiB window, content checksum) holding a compact JSON object with sorted keys, from object id to the file's contents: `{"0acd2cf2ad54":"// SPDX-License-Identifier: ...","b8e8febf8534":"..."}`. Every file of every snapshot is stored once under its object id, however many repositories, commits or collections contain it.

An object's full id is the SHA-1 git blob id of its UTF-8 contents, `sha1("blob " + byteLength + "\0" + bytes)`, which consumers compute from the bundle: it starts with the object id for objects from SHA-1 repositories, but not for those from SHA-256 ones (rule 2). Every object is a blob of this repository (rule 9), so `GET https://api.github.com/repos/<owner>/audit-dataset/git/blobs/<blobId>` returns it alone: as base64 in JSON by default, or as the raw bytes with `Accept: application/vnd.github.raw+json`. A blob id names its bytes, so the request needs no commit.

### Rules

1. **Stored bytes.** Contents are the file as stored in `audited-sources/`: the git blob at the audited commit, formatted by the `format` command with the config in `foundry.toml`, decoded as UTF-8. Object ids are therefore not upstream blob ids for files `forge fmt` changed (`git_object` in the manifest keeps the upstream provenance), and files that differ upstream only in style share one object. A symlink is stored as its resolved target. A file that does not match its manifest `sha256` or is not valid UTF-8 fails the export.
2. **Content addressed.** `sha1("blob " + byteLength + "\0" + bytes)` of the contents (sha256 for a SHA-256 repository) starts with the object id. Two different contents sharing an object id fail the export.
3. **Solidity only.** Only files ending in `.sol`. A scoped path with no Solidity files is left out.
4. **Only what was audited.** `reports` holds every relevant report and no irrelevant one, including the reports that audited no exported file (circuits, Cairo or Rust code, cryptographic reviews, scopes pinned only to branches). Snapshots hold only versions pinned to a full commit (branches, tags and pull requests without a resolved commit, and commit ranges, are left out); only files the manifest fetched (commits that could not be fetched and symlinks with missing targets are left out); no `not_audited` versions, and no file under a path the same report marks `not_audited` at that commit (a report scoping `src` and excluding `src/vendor` covers nothing under `src/vendor`). A directory scope covers no tests, mocks or deployment scripts: files with a `test`, `tests`, `mock`, `mocks`, `script` or `scripts` path segment below the scoped directory, or ending in `.t.sol` or `.s.sol`; a file scope covers its file whatever its name. Every file in a snapshot is covered by at least one of its audits, every audit covers at least one file and names a report in `reports`, and every object is used by at least one file. Two versions of one report scoping the same path at the same commit fail the export.
5. **Ids and paths.** A report in several collections is exported once, with all of them in `collections` and the `document` of the first; one id naming two different report documents (original PDF/HTML bytes) or two different titles, auditors or dates fails the export. A `document` is under `<first collection>/reports/` and ends with `.pdf`, `.html`, `.csv`, `.js` or `.md`. Every repository id is canonical: `python3 -m audit_dataset repository-id` maps the URL the id determines back to the id. Paths never end with `/`.
6. **Collections.** Every collection of the dataset is listed, including any no exported report belongs to, and every collection a report names is listed. `kind` is `library` exactly for the ids under `_libs/` (`_libs/<vendor>`) and `project` for every other id, a single directory name that is the L2BEAT project id. Names are unique, non-empty and without surrounding spaces. A `collections.json` that does not name exactly the dataset's collections fails the export.
7. **Timestamps.** Every exported commit has a timestamp: the summary's ISO 8601 UTC committer date in unix seconds. A missing timestamp, one that is not a whole second, or two versions disagreeing on one commit's timestamp fail the export.
8. **Deterministic.** Keys are sorted, except that the commits of a repository are ordered by timestamp, then commit id. The index is written with 2-space indentation and a trailing newline. The same dataset produces byte-identical files.
9. **Committed blobs.** Every object is committed in this repository as a blob with exactly its bytes: the SHA-1 git blob id of its contents is the committed blob of at least one stored copy under `audited-sources/`, so GitHub's blob API returns exactly the object. An object whose stored copies were committed with converted line endings, or changed without being committed, fails `--check`.

### Regenerating and checking

`python3 -m audit_dataset export` reads every collection with an `audit-summary.json`, validates each summary with the same checks as `render`, verifies every stored source against its manifest `sha256`, builds the export in memory, checks it against every rule above and only then writes both files. `pipeline` runs it as its last step, so the export is regenerated whenever a collection changes; commit both files together with that change.

`python3 -m audit_dataset export --check` writes nothing. It rebuilds the export, checks the committed files against every rule (including the zstd frame having exactly one frame and a content checksum), and fails if they differ from the rebuilt export by a single byte. It then reads the git index (`git ls-files --stage`), so run it on a clean checkout or after `git add`. Every object's full id must be the staged blob id of a file a `manifest.json` names (rule 9). Every report's `document` and every file a `manifest.json` names must be in the index under exactly that path, letter case included: opening a file succeeds on a case-insensitive filesystem (the macOS default) whatever its case, but not on a case-sensitive one such as Linux CI, and GitHub links are case-sensitive too. A document in another case means the summary's `report_file` disagrees with the committed report. On a case-insensitive filesystem `git add` reuses the case git already knows, so record a stored file whose case differs from its manifest path with `git mv -f <committed path> <manifest path>`.
